# ตรวจ Revision ก่อนออก Issued

พรีวิวฉบับใช้การตรวจทะเบียนและหลักฐานร่วมกันตั้งแต่ v0.76 ดู [คู่มือพรีวิวฉบับ](PUBLISHED_PREVIEWS.md) และขอบเขตหลักฐานก่อนใช้งาน

## ส่งออกและจัดชุดฉบับที่รับรองแล้ว

ในหน้าชุดส่งตรวจ เลือก **For Construction** เพื่อเลือกเฉพาะ Revision ที่ยังเป็น Issued สร้างไฟล์ใหม่หลังออกฉบับ แล้วเลือกไฟล์จาก Issued เดียวกัน ชุดที่มีไฟล์ Frozen ก่อนออกฉบับใช้สำหรับ Review หรือ Tender เท่านั้น การจัดชุดไม่อนุมัติวิศวกรรมเพิ่ม

ไฟล์ Excel/PDF ที่ออกจาก Issued ใช้ป้าย **ISSUED / FOR CONSTRUCTION** เมื่อทะเบียนออกฉบับ เหตุการณ์ บันทึกการรับรอง ชุดกฎ รุ่นคำนวณ และข้อมูลที่ตรึงไว้ตรงกัน ไฟล์จากฉบับถูกแทนที่ใช้ **SUPERSEDED / NOT FOR CONSTRUCTION** การดาวน์โหลดไฟล์เดิมจากประวัติยังคงไบต์เดิม การรวมชุดใหม่ตรวจสถานะปัจจุบันก่อนเริ่มและปิดงาน

Manifest รุ่น 2 ของชุดก่อสร้างมี `issuedReference` ระบุ `projectId`, `revisionId`, `revisionDigest`, `issuedEventId`, `issuedAt`, `issuedBy`, `ruleSetDigest`, `approvalId` และ `engineVersion` เอกสารทุกไฟล์ใช้ข้อมูลอ้างอิงชุดเดียวกัน บันทึก `issue` และ `revisionEvents` ต้องมี `revisionDigest`/`engineVersion` ตรง Snapshot ต้นทาง การเริ่ม/ปิดงานส่งออกและทำต่อ/ปิดชุดต้องตรวจข้อมูลและสถานะนี้ซ้ำในนโยบาย API หรือฝั่งเซิร์ฟเวอร์ที่เจ้าของจัดการเอง การตรวจใน client ไม่ป้องกันการข้ามขั้นผ่าน SDK/REST

ทะเบียน Excel พิมพ์ข้อมูลหลักคอลัมน์ A:I บน A3; checksum เต็ม รหัสงาน และตำแหน่งไฟล์ ZIP อยู่ในคอลัมน์ J:N ของตารางเดิม ข้อมูลชุดส่งอยู่ครบสองคอลัมน์ในหน้า Package Basis ไม่แก้เลขแบบภายใน PDF เดิม

รุ่นนี้ทดสอบไฟล์ Frozen/Draft จริงและ Backup/Restore ด้วย Firebase จำลอง ส่วน Issued ตรวจด้วยข้อมูลจำลองและ transaction doubles เท่านั้น ยังไม่ผ่านการบันทึก/ส่งออก Issued กับนโยบายจริง ผู้ใช้เป็นผู้จัดการ Rules และ deploy; ไม่มีการเปลี่ยน Rules หรือส่งเอกสารถึงผู้รับจริง

รุ่น 0.71 เพิ่มการตรวจข้อมูลใน Revision ที่ตรึงไว้ การบันทึกผลตรวจ และคำสั่งรับรองชุดกฎ/ออก Issued ระบบใช้ผลตรวจใหม่ก่อนบันทึกสถานะ ไม่ใช้ผลตรวจเก่าที่ดาวน์โหลดหรือคืนจาก Backup เป็นสิทธิ์อนุมัติ

Rules ปัจจุบันที่ผู้ใช้กำหนดยังปิดการรับรอง Spec และ Issued ไม่มีการแก้หรือ deploy Rules ในงานนี้ คำสั่งบันทึกการรับรองและ Issued ยังต้องตรวจจริงอีกครั้งหลังเจ้าของฐานข้อมูลจัดสิทธิ์ และมีหลักฐานวิศวกรรมที่ผู้รับผิดชอบรับรองครบ

## ตรวจข้อมูลที่ตรึงไว้

เปิด **แบบส่งงาน** เลือก Frozen revision แล้วกด **ตรวจความพร้อม Revision ที่เลือก** ระบบแสดงรายการทั้งหมด แยกตาม Revision มาตรฐาน สมาชิก เอกสาร ขอบเขตเหล็ก เลขแบบ และฐานปริมาณ ค้นหาชื่อสมาชิกหรือข้อความเพื่อเปิดแก้ข้อมูลทำงานได้ ผลตรวจไม่ถูกจำกัดอยู่ที่ 12 รายการแรก

การตรวจอ่านไฟล์จริงและตรวจ checksum เปรียบเทียบเอกสารฉบับปัจจุบันกับ Snapshot ตรวจว่าปริมาณ/ยาวตัด/น้ำหนักยังตรงกับฐานที่ตรึงไว้ และตรวจผลรับรอง Code99 ที่มีผลต่อ Revision นั้น เอกสารถูกแทนที่ ข้อมูลขัดกัน ชุดกรณีไม่ครอบคลุม หรือไม่มีฐานคำนวณจะยังเป็นรายการต้องดำเนินการ

ผู้ผูกกับโครงการที่มีสิทธิ์อ่านตรวจข้อมูลและเปิดประวัติได้ ผู้ดูแล/QS/ผู้ตรวจ/ผู้อนุมัติบันทึกผลตรวจได้ ผลที่บันทึกเป็น JSON มี checksum และหลักฐาน ณ เวลาตรวจ แม้ผลครบก็ไม่เป็นการออก Issued การเปลี่ยนข้อมูลทำให้หน้าจอผลปัจจุบันล้างและต้องตรวจใหม่

## สมาชิกที่ไม่มีเหล็ก

ต้องระบุขอบเขตไม่มีเหล็กและที่มาอย่างชัดเจน ไม่มี BBS หรือตารางเหล็กต้นทางที่ขัดกับคำระบุ ผู้ตรวจต้องทบทวนเอกสารสมาชิกพร้อมบันทึกเหตุผล โดยผลทบทวนผูกกับข้อความขอบเขตนั้น กรณีมีจุดชี้ Mark เก่าหรือเปลี่ยนข้อความขอบเขตต้องทบทวนใหม่

หลังตรวจเอกสารครบ สมาชิกประเภทนี้ผ่าน Checked แล้ว ApprovedForIssue ได้โดยไม่สร้างเหล็กสมมติ สมาชิกที่ยังไม่กรอก BBS และไม่มีคำระบุขอบเขตยังถูกปฏิเสธ การคืนข้อมูลทำงานจาก Backup ยังคงเป็น Draft และล้างผลทบทวนเอกสาร

## รับรองชุดกฎ

เจ้าของฐานข้อมูลต้องเปิดสิทธิ์เก็บกรณีและผลตรวจ และเปิด `VITE_ENABLE_ENGINEERING_FIXTURES` ก่อนใช้คลังกรณีที่บันทึก ใน General Spec ให้ระบุปีฉบับ ACI ผู้รับผิดชอบ ที่มาชุดกฎ และคำอธิบายชุดกรณีอ้างอิงก่อนเก็บ/เทียบกรณี

ผู้อนุมัติในทีมเลือกหลักฐานโครงการฉบับปัจจุบันที่ทบทวนแล้ว และผลตรวจที่รวมกรณีบวกและลบ แอปตรวจตัวเลขซ้ำตามค่าที่กรอก ตรวจ Spec/รุ่น/ข้อมูลและไฟล์อ้างอิง แล้วบันทึกการยืนยันของผู้อนุมัติ ชุดรับรองระบุ Category และ Shape code ที่มีกรณีบวกครอบคลุม รหัสกรณีและ checksum ถูกเก็บในบันทึกแยกจากข้อความอธิบาย Spec

การยืนยัน ACI เป็นการทบทวนหลักฐานโดยผู้รับผิดชอบ ไม่มีการอ้างว่าแอปตรวจทุกข้อ ACI อัตโนมัติ การผ่านผลเปรียบเทียบกับค่าที่กรอกไม่พิสูจน์ว่าค่าอ้างอิงถูกต้อง ผู้อนุมัติต้องตรวจเอกสารอิสระและความเหมาะสมของขอบเขตเทียบเอง รูปที่ระบบยังไม่รองรับรายละเอียดจริง เช่นการปิดปลายรูป 33/51 ยังคงมีข้อจำกัดเดิม

## ออก Issued

เมื่อผลตรวจ Revision ปัจจุบันไม่มีรายการค้าง ผู้อนุมัติในทีมกรอกบันทึกการออกฉบับแล้วกด **ออก Issued จาก Revision ที่ตรวจครบ** แอปตรวจหลักฐานใหม่ก่อน commit ตรวจรุ่นข้อมูลและสถานะ Frozen ซ้ำใน transaction แล้วเขียนสถานะและเหตุการณ์ Issued พร้อมรหัสการรับรองชุดกฎในครั้งเดียว

การ Retry ด้วยรหัสคำขอเดิมคืนผลเดิมโดยไม่ออกฉบับซ้ำ เมื่อข้อมูล/สิทธิ์/สถานะเปลี่ยนระหว่างตรวจ คำสั่งปฏิเสธผลที่ล่าช้า การสร้างไฟล์จาก Issued/Superseded ตรวจความตรงกันของทะเบียน เหตุการณ์ และบันทึกอนุมัติเดิมก่อนใช้ป้ายสถานะนั้น ฉบับ Frozen ต้นทางและตัวเลขไม่ถูกแก้ทับ

## สัญญาข้อมูลสำหรับเจ้าของ Rules หรือ API

แนวทางนี้เป็นข้อกำหนดของคำสั่งแอปให้เจ้าของนำไปจัดนโยบายเอง ไม่ใช่ Rules ที่ deploy แล้ว

| คำสั่ง | สิทธิ์และข้อมูลที่ต้องอนุญาตพร้อมเงื่อนไข |
| --- | --- |
| กรณี/ผลตรวจ | ผู้เตรียมและผู้ตรวจตามทีม อ่าน/สร้างกรณีและผลเทียบแบบไม่แก้ทับ พร้อม `historyEpoch` และ `engineeringFixtureEpoch` ตามสัญญาเดิม |
| `approveEngineeringSpec` | ผู้อนุมัติในทีม ยืนยัน Spec/หลักฐาน/ผลตรวจที่ตรงรุ่น อัปเดตเฉพาะสถานะการรับรองและหลักฐานของ Spec โดยไม่เปลี่ยนตัวเลข พร้อมเพิ่ม version และบันทึก operation UID ตรงผู้ใช้ |
| `prepareIssue` | ผู้ดูแล/QS/ผู้ตรวจ/ผู้อนุมัติ บันทึกไฟล์ผลตรวจแบบ immutable ใน snapshots พร้อม operation และเพิ่ม project version ผลตรวจนี้ไม่ให้สิทธิ์ออกฉบับ |
| `issue` | ผู้อนุมัติในทีม เฉพาะ Frozen ที่มีหลักฐานครบ อัปเดต revisionStates เป็น Issued พร้อม `issuedAt`, `issuedBy`, `ruleSetDigest`, `approvalId`, `issuedEventId`; สร้าง revisionEvents และ operation ที่สอดคล้องกัน พร้อมเพิ่ม project version |

นโยบายต้องแยกโครงการ/ผู้ใช้ บังคับ UID และบทบาทของทุก action ป้องกันการเขียนผ่าน SDK/REST ที่ข้ามขั้นตรวจ และป้องกันการแก้ทับกรณี ผลตรวจ เหตุการณ์ และไฟล์ การตรวจใน client ไม่แทนการบังคับข้อมูลและกฎวิศวกรรมใน API/นโยบายฝั่งเซิร์ฟเวอร์ การใช้ current Rules ที่ปิดอยู่ย่อมยังปฏิเสธ Spec approval และ Issued

Backup รวมเฉพาะประวัติ operation ของการตรวจ/รับรอง/ออกฉบับที่เกี่ยวข้องพร้อมไฟล์ผลตรวจ Restore เก็บทั้งหมดเป็น importedHistory อ่านอย่างเดียว ไม่สร้าง operation อนุมัติหรือสถานะ Issued ในโครงการใหม่

## ผลทดสอบและงานก่อนใช้จริง

ทดสอบขั้นทบทวนเอกสารไม่มีเหล็กและสถานะสมาชิก ตรวจ Frozen 16 สมาชิกที่มีรายการค้าง 48 รายการ บันทึก/เปิดประวัติ ค้นหา desktop/mobile สิทธิ์ Viewer และ UID รวมถึง Backup/Restore กับ Firebase จำลองจริง ส่วน positive commit ของ Spec approval และ Issued ทดสอบด้วย transaction doubles เท่านั้น Rules เดิมยังปฏิเสธการเขียนสถานะที่ปิดไว้ ไม่ใช่การตรวจรับ Production หรือวิศวกรรม

ต้องทดสอบการบันทึกรับรอง/Issued การส่งออกและการรับรองเจ้าของงานกับนโยบายจริงหลังผู้ใช้จัดสิทธิ์ พร้อมกรณีวิศวกรรมและแบบโครงการจริง งาน GULF/วัสดุ/รายละเอียดปิดปลาย การใช้ stock/offcut และการตรวจรับระบบเต็มยังไม่เสร็จ
