# Authentication and project access — direct SDK

v0.44 initializes Auth with browserLocalPersistence first and indexedDBLocalPersistence second, plus browserPopupRedirectResolver. The unchanged login service already chooses browserLocalPersistence. Consistent preference at startup/login avoids the reproduced v0.43 symptom where a new getAuth tab migrated localStorage state into IndexedDB and signed the original tab out. The installed @firebase/auth1.13.6 SDK migrates an existing IndexedDB user into the preferred store and clears the previous user entry after successful migration; this is verified with actual old/new compiled bundles on one origin. Explicit initialization and default dependency ordering are documented in [Firebase's primary guide](https://firebase.google.com/docs/auth/web/custom-dependencies). Storage remains managed by Firebase, with no token-copy code, custom storage broadcasts or injected events.

Before using a new release on an existing app origin, close/reload every older BOQ/BBS tab so all running tabs use the same initialization preference. Old getAuth tabs can still prefer IndexedDB; simultaneous mixed releases are outside acceptance. The verified migration preserves an existing login and logout clears both stores. These checks cover local Chromium and email/password login; live Google OAuth, other browser engines, blocked browser storage, offline/queued writes and production Rules require their own acceptance. Login still requires the existing service's localStorage availability; the migration fallback is not a promise of login support in storage-blocked browsers. Firebase's [persistence guide](https://firebase.google.com/docs/auth/web/auth-state-persistence) describes domain-local persistence and same-origin tab synchronization; separate browsers/origins do not share this session.

Evidence: [v0.44 before/after report](../output/auth-persistence-verification/DEVELOPMENT_REPORT.html).676 existing unit tests and17 actual UI/access/upgrade paths pass. AuthContext.tsx/authService.ts, Firestore/Storage Rules, .env and firebase.json remain byte-identical. The previous compiled cross-tab timeout is resolved within the stated scope. This is not engineering, owner or production acceptance.

Use the Firebase values already in `.env`: API key, project ID, Auth domain, Storage bucket and app ID. They configure the Firebase SDK; there is no separate API URL or Cloud Functions endpoint. Never put an Admin SDK/service-account secret in Vite variables.

App profiles use `my-boq-app/root/users/{lowercase email}` and bind both Auth UID and email. Registration atomically pairs the first approved MasterAdmin with bootstrap metadata; later users are Staff pending. Simultaneous first registrations elect one MasterAdmin. Registration fills empty form fields when AuthContext created the record first. Existing names/timestamps are preserved. First MasterAdmin cannot be rejected or demoted by the application or Rules.

Only MasterAdmin lists private profiles and manages approval/global roles/project assignments. Approved users see assigned projects; MasterAdmin has system-wide project access. Roles form a union, with explicit project overrides. Directory projections expose UID/email/name/approval/version for project-team lookup, without exposing position/department/full assignments. Directory status represents app approval, not a Firebase Auth console account-status lookup. Rejecting an app profile denies subsequent Firestore/Storage requests using its current token.

Own-profile fields are editable with optimistic profileVersion and stable request replay. Live updates preserve unsaved form data; stale saves stay open. Removing edit roles disables member fields already open while retaining draft text. Auth UID replacement cannot inherit an old approved profile merely by reusing an email.

Firebase console setup: enable Email/Password and Google as required; set the actual app host under authorized domains; confirm the configured bucket exists and Storage is enabled. The user defines and deploys Firestore/Storage Rules. The user explicitly declined agent deployment on 2026-10-12 and reaffirmed that decision on 2026-10-14; do not deploy or replace the live Rules. This latest decision supersedes earlier permission to deploy project-isolation Rules. Local proposed Rules support development checks only until the user's deployed Rules are independently verified against the application contract. Current QA uses explicitly configured demo emulators only; live Google login/domain and production operations are not claimed accepted.

If changing VITE_APP_NAME, also update and verify the namespace in both Rules files. Current default is my-boq-app. There is no automatic anonymous/shared workspace. Cloud Functions is not needed.

For local QA, pin VITE_USE_EMULATORS=true, demo-boq-bbs project/API/bucket/Auth domain and app ID in the test process. Do not replace the production `.env`.
